# ワークフロー承認シート → マイチャット通知

対象スプレッドシート: `ワークフロー承認シート`
（ https://docs.google.com/spreadsheets/d/1YCn1SUWyAX8sTqqK6SMR0JUEbRCMBax9aWymMXe_zCc/edit ）
対象タブ: `新ワークフロー`（案件管理表）

「新ワークフロー」シートが以下のタイミングで更新されたら、Gemini APIで
「考察」「承認にあたっての検討事項」を自動生成し、Chatworkの自分のマイチャットへ
リアルタイムで通知します。

- (A) 新規申請行が追加された（会社名・申請内容が入力された）とき
- (B) 2次承認が完了し、最終承認待ちの状態になったとき
  （＝最終承認者がこれから承認判断をする直前のタイミング。事後報告ではなく、
  　判断前に考察・検討事項を届けることを想定）

「フロントページ」「議事録起票」列にURLが入っている場合は、そのページの内容も
取得してGeminiへの入力に含める。

- NotionのURL（`notion.so` / `notion.site` / `notion.com`）は、Notionは画面を
  JavaScriptで描画するため単純なHTML取得では中身が読めない。そのため
  **Notion公式APIを使って本文を取得する**（下記セットアップが必要）。
- それ以外のURL（自社EC・LPなど通常のWebページ）は、HTMLを取得しタグを除去した
  テキストをそのまま使う。
- 取得できない場合（未共有・未設定・ログイン必須ページ等）は「取得できません
  でした」として無視され、考察が憶測で埋められることはない。

### Notion連携のセットアップ（フロントページ／議事録リンクを読み込む場合に必要）

1. https://www.notion.so/my-integrations で「Internal」インテグレーションを新規作成し、
   対象のNotionワークスペースを選択する
2. 発行された「Internal Integration Secret」を控える
3. スクリプトプロパティに `NOTION_TOKEN` として登録する（**コードに直接書かない**）
4. フロントページ・議事録として使っているNotionページ（またはその親ページ／
   データベース）を開き、「•••」→「Connections」から作成したインテグレーションを
   追加して共有する（個別ページより親ページをまとめて共有する方が運用しやすい）

`NOTION_TOKEN` が未設定の場合や、対象ページがインテグレーションに共有されて
いない場合は、その旨が考察に「取得できませんでした」と明記され、処理自体は
止まらない。

このスクリプトはGoogle Apps Script（スプレッドシートのコンテナバインドスクリプト）
として動作します。GitHub Actionsではなく、スプレッドシート側で完結する仕組みです。
このディレクトリはソースの保管・レビュー用であり、実際に動かすには下記の手順で
対象スプレッドシートに手動で貼り付ける必要があります（Apps Script APIへの
自動デプロイはこのセッションのツールでは行えません）。

## セットアップ手順

1. 対象スプレッドシートを開き、「拡張機能 > Apps Script」を開く
2. デフォルトの `コード.gs` の中身を、このディレクトリの `Code.gs` の内容で置き換える
3. `appsscript.json`（表示 > マニフェスト ファイルを表示、で表示される）の内容を
   このディレクトリの `appsscript.json` に置き換える
4. スクリプトエディタ左メニューの「プロジェクトの設定」→「スクリプト プロパティ」で
   以下を登録する（**コードに直接書かない**）
   - `GEMINI_API_KEY` : Gemini APIキー（未設定でも動くが、その場合は定型文フォールバックになる）
   - `CHATWORK_TOKEN` : マイチャットの送信先アカウントのChatwork APIトークン
   - `MYCHAT_ROOM_ID` : マイチャットのルームID
     （Chatworkでマイチャットを開いたときのURL `https://www.chatwork.com/#!ridXXXXXXXX` の数字部分）
5. スクリプトエディタで関数 `setupTrigger` を選択して一度だけ実行し、
   インストール型のonEditトリガーを作成する（初回のみ承認ダイアログが出るので許可する）
6. 動作確認: 関数 `testNotifyRow` を `testNotifyRow(42, "new")` のように直接実行し、
   マイチャットにメッセージが届くか確認する（`42` は実データがある行番号に置き換える。
   `"final_pending"` を渡せば最終承認待ちパターンのテストもできる）

## 列の解決方法（列番号を固定せず、見出し文字列で毎回自動解決）

このシートは列の追加・並び替えが頻繁に発生する（実際に運用中、短期間に
複数回列構成が変わり、固定の列番号ハードコードでは何度も壊れた）。そのため
`Code.gs` の `resolveColumns_()` は、毎回シートの見出し行（`HEADER_ROW` =
2行目）を読み取り、以下の見出し文字列に一致する列を探して使う。**列番号は
どこにもハードコードしていない**。

| 見出し文字列 | 用途 |
|---|---|
| `会社名` | 会社名 |
| `弊社担当者` | 弊社担当者 |
| `商材プラン1` | 商材プラン |
| `ステージ` | 商談ステージ |
| `一次商談日` | 一次商談日 |
| `フロントページ` | Notion等のURL（内容取得の対象） |
| `議事録起票` | Notion等のURL（内容取得の対象） |
| `取引先登録申請書` / `反社チェック` / `NDA` / `契約書回収` | コンプライアンス進捗 |
| `本提案_日付` | 本提案日 |
| `申請内容` | 申請内容本文 |
| `セールス 承認` | セールス承認チェック |
| `1次 承認者` / `1次 承認` | 1次承認 |
| `2次 承認者` / `2次 承認` | 2次承認（このチェックがtrueになった時点が「最終承認待ち」トリガー） |
| `最終 承認者` / `最終 承認` | 最終承認（`最終 承認者`列が存在しない構成でも動く） |
| `承認理由` | 各承認チェック列の**直後**にある場合のみ、その承認の理由として拾う（同じ見出しが複数回出るため、位置で判定） |

見出し文字列そのものが変わった場合（例:「会社名」を「取引先名」に変更した等）は、
`resolveColumns_()` 内の該当する `indexOf('...')` の文字列を実物に合わせて
書き換える必要がある。それ以外（列の追加・削除・並び替え）は、見出し文字列さえ
一致していれば自動的に追従する。

シート名・見出し行位置・A1のルール文セル位置が変わった場合は、`Code.gs` 冒頭の
`WORKFLOW_SHEET_NAME` / `HEADER_ROW` / `RULE_TEXT_CELL` を修正すること。

## 記入例・テンプレート行への誤通知対策

シートに記入例として残っている行（例:「株式会社サンプル商事」）が誤って
編集されると、本物の新規申請と誤認して通知してしまうことがある（実際に一度
発生した）。`Code.gs` の `PLACEHOLDER_COMPANY_NAMES` に会社名を追加しておくと、
その会社名の行は通知対象から除外される。

## 通知が重複しない仕組み

同じ行に対して同じステージ（新規申請/最終承認待ち）の通知は1回のみ送るよう、
`PropertiesService`（スクリプトプロパティ）に送信済みフラグを保存しています。
再送したい場合は、対象キー（`notified_new_row<行番号>` / `notified_final_pending_row<行番号>`）を
スクリプトプロパティから手動削除してください。

## タスク登録について

マイチャットは自分の発言が常に既読扱いになる仕様上、メッセージだけではバッジが
付かず見落とされやすい。そのため、通知メッセージの送信に加えて、同じ内容を
**自分宛てのChatworkタスク**としても登録している（`postTaskToMyChat_`）。
タスクはChatworkの「タスク一覧」・未完了タスクのバッジに残るため、完了操作
（チェックを入れる）をするまで見落としにくい。

自分のChatworkアカウントIDは初回実行時にAPI（`GET /me`）で自動取得し、
スクリプトプロパティ `CHATWORK_ACCOUNT_ID` にキャッシュされる（手動設定不要）。

## セキュリティ上の注意

- APIキー・トークンはすべてスクリプトプロパティに保存し、コードにはハードコードしていません。
- このスクリプトが叩く外部サービスは Gemini API と Chatwork API のみです。
